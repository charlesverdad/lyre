# LEARNINGS

Operational gotchas for future agents. Newest first, concise.

## v0.4.0 task F1 — Capacitor Android scaffold + nix toolchain (2026-08-01)

- **AGP 8.13's default `buildToolsVersion` is hardcoded (35.0.0) and does NOT track `compileSdk`.** Pinning `buildToolsVersion` in `android/app/build.gradle` alone is not enough: every Gradle _library_ module pulled in from `node_modules` (`capacitor-android`, `capacitor-app`, `capacitor-cordova-android-plugins`, each with its own `android { }` block) independently falls back to that same hardcoded default and tries to auto-resolve/download it. Against a normal writable SDK install this "just works" (silently fetches 35.0.0 alongside your real version); against the nix-built SDK (read-only store path, only the one build-tools version you selected actually exists) it hard-fails with `The SDK directory is not writable`. Fix: force it for _every_ subproject from the root `android/build.gradle`'s `allprojects { afterEvaluate { project.android.buildToolsVersion = "<pinned>" } } }`, not just the app module.
- **`android-nixpkgs`'s `sdk.nix` needs no explicit license-acceptance step** — the derivation stamps every required license hash into the SDK tree's `licenses/` dir as part of the build itself, so there's nothing like `sdkmanager --licenses` to run in `shellHook`. Confirmed by inspecting `pkgs/android/sdk.nix` in the fetched repo: it builds a `linkFarm` of license-hash files from each selected package's `license.hash` and includes it in `buildInputs`.
- **Non-flake, non-channel `android-nixpkgs` import**: `pkgs.callPackage (import (builtins.fetchGit { url = "https://github.com/tadfisher/android-nixpkgs.git"; rev = "<pin>"; })) { channel = "stable"; }`, then `android-nixpkgs.sdk (sdkPkgs: with sdkPkgs; [ cmdline-tools-latest platform-tools platforms-android-36 build-tools-36-1-0 ])`. Package names for a given Android version follow `build-tools-<major>-<minor>-<patch>` / `platforms-android-<major>` (dashes, not dots/semicolons) — check `channels/stable/default.nix` in the fetched repo for exact available names/revisions before pinning (e.g. `build-tools-36-1-0` was the newest 36.x at pin time, not `36-0-0`).
- **ESLint's `includeIgnoreFile(gitignorePath)` only parses the one `.gitignore` path given to it — it does not cascade into nested `.gitignore` files.** Committing `android/` (which has its own `.gitignore` covering `build/`, `app/src/main/assets/public` (the `cap sync`-copied web build), `.gradle/`, `local.properties`, `*.apk`) does not stop root ESLint/Prettier from trying to lint/format those copied `.js` files — they aren't tracked by git, but they exist on disk after any `cap sync`/build. Needed an explicit `ignores: ['android/**']` entry in `eslint.config.js` and `/android/` in `.prettierignore`, layered on top of (not instead of) `android/.gitignore`.
- **`just build`/`just android-build` are not byte-reproducible across separate invocations even with identical source** — SvelteKit embeds a build timestamp in `_app/version.json`, which cascades into every chunk's content hash and therefore every filename referencing it. This is expected noise, not a regression signal: diff `index.html`/JS _content_ for the actual thing that matters (e.g. absence of `/lyre` in asset URLs), not raw hashed filenames, when comparing two builds.
- **No emulator or device was available in this environment** (`adb devices` empty; no `system-images`/`emulator` packages were added to `shell.nix` — deliberately out of scope for a timeboxed toolchain task) — the debug APK was verified by building it (`./gradlew assembleDebug` succeeds), unzipping it, and grepping the bundled `assets/public` for the `/lyre` base path (absent, as required), but it was never actually installed or launched. A real device/emulator smoke test is still open for a future task.

### Follow-up review round (same day) — emulator smoke test caught what static reading missed

- **SvelteKit auto-registers `src/service-worker.ts` regardless of any app-level guard, because `kit.serviceWorker.register` defaults to `true`.** The `Capacitor.isNativePlatform()` guard around the manual `navigator.serviceWorker.register(...)` call in `+layout.svelte` was necessary but not sufficient — Kit's own injected registration script runs unconditionally, on every platform, so the native app still ended up with a live service worker registration (`getRegistrations().length === 1`) despite the guard "reading correctly." A prior static review pass concluded the guard was "correct and fails safe" — that conclusion was wrong, and only running the actual APK and querying `navigator.serviceWorker.getRegistrations()` from a live page (see next bullet) surfaced it. Fix: `serviceWorker: { register: false }` in `vite.config.ts`'s `sveltekit({...})` options, making the guarded manual call in `+layout.svelte` the single registration path. **Lesson: never certify a runtime guard as correct from reading the code alone when the framework has its own opinion about the same resource — check for framework-level auto-behavior first.**
- **Chrome DevTools Protocol over `adb forward` is the reliable way to assert live in-app JS state (service worker registrations, `window.Capacitor.isNativePlatform()`, safe-area CSS var values, or to drive the SPA's own client-side router instead of fighting physical tap coordinates on a slow/jank-prone emulator).** `pid=$(adb shell pidof <package> | tr -d '\r'); adb forward tcp:9222 localabstract:webview_devtools_remote_$pid; curl -s http://localhost:9222/json` lists the page (and any `service_worker` targets) with a `webSocketDebuggerUrl`. A ~40-line Node script opening that as a `WebSocket` and sending `Runtime.evaluate` (`awaitPromise: true, returnByValue: true`) round-trips arbitrary async JS, including clicking buttons by text content (`[...document.querySelectorAll('button')].find(...).click()`) when `input tap` coordinates are unreliable. Re-forward the port after every app restart/reinstall — the socket name embeds the OS pid and goes stale silently (old forward just times out, no error).
- **`adb exec-out screencap -p > file.png` gets corrupted when the invoking shell (here, `nix-shell`'s `shellHook`) writes a banner to stdout first** — the PNG bytes get interleaved with shell text and the file doesn't decode. `adb shell screencap -p /sdcard/s.png && adb pull /sdcard/s.png <local path>` avoids the problem entirely (writes to the device's filesystem, then a clean binary pull) and should be the default for any screenshot taken from inside a wrapped/`nix-shell`'d command.
- **A software-rendered (`-gpu swiftshader_indirect`) emulator under host contention produces multi-hundred-millisecond to multi-second frame latency (`Davey!` warnings in logcat) and spurious "X isn't responding" ANR dialogs for unrelated system apps (e.g. Pixel Launcher)** — these interceptor dialogs steal the next tap if you don't dismiss them first, and `adb shell input tap` fired immediately after `am start` or a UI transition can land before the frame it was aimed at is actually presented, silently hitting whatever was still on screen. Poll for actual state (`dumpsys activity activities | grep topResumedActivity`, or a CDP `Runtime.evaluate` reading `location.href`/DOM content) before tapping or screenshotting, rather than a fixed sleep; prefer driving the app via CDP JS over synthetic taps entirely once the WebView's devtools port is reachable.
- **A crashed/killed emulator process can leave `~/.android/avd/<name>.avd/*.lock` files behind**, which makes the next `emulator -avd <name>` launch fail immediately with `FATAL: Running multiple emulators with the same AVD is an experimental feature` even though no other instance is actually running. `rm ~/.android/avd/<name>.avd/*.lock` before relaunching fixes it; check `ps aux | grep qemu` first to make sure nothing genuinely is still running.
- **Nix SDK store paths are content-addressed and change whenever the deriving `.nix` file changes** (here, adding `emulator`/`system-images-*` packages to the Android shell) — a Gradle daemon started against the old path keeps using it until stopped, so a build immediately after a `shell*.nix` edit can fail with `package android.* does not exist` even though the new path's `android.jar` is present and correct. `cd android && ./gradlew --stop` before rebuilding is the fix; this is now called out directly in `shell-android.nix`'s own `shellHook`.
- **Files a Capacitor CLI command (`cap sync`/`cap update`) regenerates from scratch every run should be gitignored, not committed** — `android/capacitor.settings.gradle` bakes in pnpm's exact virtual-store paths for the installed `@capacitor/*` versions (e.g. `.pnpm/@capacitor+android@8.5.0_@capacitor+core@8.5.0/...`), which breaks on any version bump or pnpm layout change until someone remembers to re-run `cap sync`. Verified empirically (delete the file, run `cap sync android`, diff — byte-identical regeneration) before gitignoring it; the general principle is "if deleting a committed file and rerunning the tool that owns it reproduces it exactly, it shouldn't be committed."
- **Capacitor 8's `SystemBars` plugin logs (not throws) `Error injecting safe area CSS: TypeError: Cannot read properties of null (reading 'style')` on some cold starts** — its `load()` synchronously calls `initSafeAreaCSSVariables()`, which `evaluateJavascript`s a `document.documentElement.style.setProperty(...)` snippet before the WebView has necessarily loaded any document (still on `about:blank` mid-navigation); the snippet's own `try { ... } catch(e) { console.error(...) }` swallows the resulting `TypeError` so it never crashes anything, only logs. Also added `viewport-fit=cover` to `src/app.html`'s viewport meta (task requirement anyway: it's what lets the WebView populate the standard `env(safe-area-inset-*)` values `layout.css` already reads, independent of Capacitor's own `--safe-area-inset-*` custom-property injection, which this app's CSS doesn't consume). After that change, three independent cold starts (fresh install, `am force-stop` + relaunch, and a from-scratch APK rebuild) on a real emulator produced zero occurrences of the error in logcat, and `getComputedStyle(document.documentElement).getPropertyValue('--safe-top')` resolved without clipping content behind the status/nav bars on four different screens (list, form, detail, bottom sheet) — logged as fixed, with the caveat that the underlying race is inside `node_modules/@capacitor/android` source and could theoretically still fire under different timing (harmless if so, per the try/catch).
- **A `just`/Makefile recipe that only works when a previous recipe already ran should declare that as a real dependency (`recipe-b: recipe-a`), not a comment** — `android-assemble` (bare `./gradlew assembleDebug`) looked self-contained but Gradle's settings evaluation needs several `cap sync`-generated, gitignored files (`capacitor.settings.gradle`, `capacitor-cordova-android-plugins/`, `app/src/main/assets/public`) that only `android-build` produces. A fresh clone running `just android-assemble` standalone got a confusing Gradle settings-evaluation error pointing at `cordova.variables.gradle`, not an obvious "run android-build first" message — `just`'s own dependency graph (`android-assemble: android-build`) makes the correct order the only order, rather than relying on doc-comment discipline.
- **A multi-GB dependency (Android SDK + JDK) that only one workflow needs shouldn't live in the shell every contributor enters by default** — split into `shell-android.nix` (Android toolchain, `nix-shell shell-android.nix`) separate from the lean default `shell.nix` (node/pnpm/just only), so `just dev`/`just verify` don't force-realize the Android closure. Bonus: `builtins.fetchGit` for `android-nixpkgs` runs at Nix _evaluation_ time, before any build step — folding it into the default shell meant even entering the shell required network access to github.com; contributors offline or behind a restrictive proxy couldn't get a shell at all for pure web work. Always pass both `ref` and `rev` to `fetchGit` when pinning a commit that isn't on the repo's default branch tip forever — a bare `rev` resolves the fetch against the ref's current HEAD and only then checks out the pinned commit, which breaks if that commit ever stops being reachable from the (implicit, unpinned) ref (e.g. a force-push).

## v0.3.0 task E4 — collections e2e + docs sync (2026-07-29)

- **An e2e "regression test" for a fixed bug can pass against both the fix and the bug, and the only way to know is to actually put the bug back and watch the test run.** First draft of a cross-tab-safety spec had tab A land on `/library` (which itself calls `createLiveQuery`, i.e. subscribes) between the two writes, then re-`goto('/library')` — a full reload that re-reads `localStorage` from scratch — so the write that mattered started from fresh state no matter what. A rewrite moved tab A to `/edit/[songId]` (whose own load, `getSongWithDetails`, is a plain `store.read`, not a live query) reasoning that this was the one screen that never calls `subscribe()`. It still didn't catch the bug when actually tested against it (see next bullet) — **and the fact that it _looked_ airtight on paper is exactly why the empirical check matters more than the reasoning.**
- **Root-layout-level side effects can make a whole class of e2e regression test structurally impossible, and only running the deliberate-break check reveals it.** `src/routes/+layout.svelte`'s `onMount` calls `defaultStore.subscribe(refreshMigrationStatus)` unconditionally, on _every_ route, for the migration-failure retry banner (task E1 review fix). That means every screen in the real app — including `/add`, `/edit/[songId]`, `/settings`, all believed to be "non-subscribing" — actually does subscribe, moments after mount, regardless of route. So the historical "a tab that never calls `subscribe()` keeps a stale cache forever" defect (`LyreStore`'s constructor vs. lazy-`subscribe()` cache-invalidation bug, task E1) **can no longer be reproduced through any real page navigation**, full stop — there is no reachable screen left that avoids the root layout's own subscription. Confirmed by temporarily moving `#attachStorageListener()` from the constructor back into `subscribe()` (the historical bug) and re-running the e2e spec: it still passed. Lesson: when a "the only non-subscribing screen is X" argument is load-bearing for a test's teeth, grep the _root layout_ for `subscribe`/`createLiveQuery` too, not just the target screen — shared shell code is an easy blind spot.
- **The existing unit-level regression test for this exact bug (`src/lib/db/store.test.ts`, "invalidates its cache on a cross-tab write even when subscribe() was never called", written in task E1) was itself toothless and had been since it was written** — its final assertion read `tabB.read((doc) => doc.songs)`, i.e. tab B's own in-memory cache, which is untouched by tab A's `mutate()` regardless of whether that write clobbered the shared underlying storage. The fix: assert against the raw persisted bytes (`JSON.parse(storage.getItem(LIBRARY_STORAGE_KEY)!)`), which is what a third tab (or either tab after a reload) would actually see. Verified with the same deliberate-revert technique: failed against the bug, passed against the fix, only _after_ the assertion-target fix — proof that "there's already a test for this" is not the same as "that test has teeth"; re-run it against a deliberately reintroduced bug before trusting it, especially for concurrency/multi-instance scenarios where it's easy to assert against the wrong instance.
- **Two genuinely separate `browser.newContext()`s do NOT share `localStorage`** — Playwright isolates storage per `BrowserContext`, so any cross-tab scenario has to be expressed as two `Page`s off **one** `context` (`context.newPage()` twice), which is the actual Playwright equivalent of two real browser tabs on the same origin.
- **`getByText('Add your first song')` is ambiguous on the empty-library state**: `EmptyState`'s title (`<p>`) and its action `Button`'s visible label are the identical string, so an unscoped text locator resolves to 2 elements and throws a strict-mode violation. Scope to the tag (`page.locator('p', { hasText: … })`, matching `library-empty.spec.ts`'s existing pattern) or to a role that only one of the two has.
- **The `Sheet`-stays-mounted-while-closed hazard (see E3 notes below) also breaks naive DOM-order/position assertions, not just click targeting**: after opening and closing the collection screen's "Add songs" sheet (which lists every library song), the same song titles exist twice in the DOM — once in the real, on-page row, once in the now-hidden-but-still-mounted sheet. An unscoped `getByText(title, { exact: true }).first()` for a reorder-order check can silently grab the _sheet's_ copy instead of the page's. Fixed with an XPath locator that explicitly excludes any `button` with a `dialog` ancestor (`e2e/helpers.ts`'s `rowByTitle`) — a small addition to the existing "always scope inside `dialog[open]`" rule: sometimes you need to scope things _outside_ every dialog instead.
- **A `ListItem` row (a `<button>`) can contain another interactive `<button>` (its trailing overflow icon) as a real DOM child** — invalid HTML nesting by the spec, but harmless here because Svelte builds the DOM via `createElement`/`appendChild`, not `innerHTML` parsing, so there's no browser normalization step to strip it. Playwright locator-scoping into the outer row (`row.getByRole('button', { name: 'Song options for …' })`) works exactly as expected; each button's own `onclick` calls `event.stopPropagation()` so the inner click never bubbles into the outer row's navigate handler.
- **A doc-only PR still needs the full `just verify`/`just build` gate re-run after the very last markdown edit** — trivial in theory, but this release's own history (per the note in this task's brief) had a Prettier miss slip through on a markdown-only change twice already; running the gate is cheaper than re-litigating that.

## v0.3.0 task E3 — collections UI (2026-07-29)

- **A named `Snippet` prop wrapped in `{#if}` at the call site breaks svelte-check**: `<TopBar>{#if cond}{#snippet actions()}…{/snippet}{/if}</TopBar>` fails typechecking ("Object literal may only specify known properties, and 'children' does not exist in type 'Props'") because the compiler can't statically see `actions` as a snippet prop when it's conditionally present — it falls back to treating the tag's contents as implicit `children`, which `TopBar`'s `Props` doesn't declare. Fix: always emit the `{#snippet}` block unconditionally and put the `{#if}` _inside_ it (renders nothing when false). Same rule applies to any named-snippet prop (`leading`, `action`, …), not just `actions`.
- **A dynamic-`[param]` route under `(app)/` needs its own `+page.ts` with `export const prerender = false`**, exactly like `song/[songId]` and `edit/[songId]` already do — otherwise `just build`'s prerender crawl throws `routes were marked as prerenderable, but were not prerendered` for the new route, since the root layout sets `prerender = true` globally and this app has no server to fall back to at request time (adapter-static + SPA fallback only kicks in for routes explicitly opted out). Easy to miss because `just typecheck`/`just test`/`just lint` all stay green without it — only `just build` (and therefore `just e2e`, which builds first) catches it.
- **`Sheet`'s content stays mounted (just CSS-hidden) while closed** — a closed sheet's rows are still real DOM nodes with real accessible names/text, so any Playwright locator that isn't scoped to a specific container (`getByText`, unscoped `getByRole`) can resolve to 2+ elements once a second sheet or the underlying page repeats the same text (e.g. an "Add songs" sheet listing all library songs, one of which is also a row title on the page behind it). Scope with `page.getByRole('banner').getByLabel(...)` for TopBar actions specifically, `.first()` for "assert the on-page copy is visible" checks, and prefer `not.toBeVisible()` over `toHaveCount(0)` when a hidden duplicate is expected to remain in the DOM (e.g. a song removed from _this_ collection still appears in the collection-agnostic "Add songs" library list).
- **Two independent `createLiveQuery` effects in the same component is the normal shape for a screen with two live lists** (e.g. the library screen's Songs-mode song list and Collections-mode collection list, or the collection screen's own-collection detail query plus the Add-songs sheet's whole-library query) — no interference between them since each owns its own `$state` handle and `untrack`-seeded initial value; cheap enough to just let both run continuously rather than gating one on which UI mode is currently visible.
- **A closed `Sheet`'s still-mounted content isn't just a Playwright locator-scoping nuisance (bullet above) — it's an interaction hazard for anyone driving the real UI (manual QA or a browser-automation agent) too.** A `find`/click helper that matches by visible text or accessible name can resolve to the _hidden_ sheet's element (e.g. a stale "Delete collection" button in a closed confirm sheet) instead of the currently-open one's, and clicking a closed `<dialog>`'s content is a silent no-op — no error, no navigation, nothing — which reads exactly like "the click landed but nothing happened" rather than "wrong element." When a click on what looks like the right label does nothing, check whether another sheet with overlapping copy is mounted-but-closed before assuming the app is broken.
- **Review-round correctness bugs worth naming for the pattern, not just the fix**: (1) a `$derived` guard that checks `handle?.value !== SENTINEL` is _not_ equivalent to `handle !== undefined && handle.value !== SENTINEL` — before the owning `$effect` has run once, `handle` itself is `undefined`, and `undefined !== SENTINEL` is `true`, so a "not loaded yet" state can misread as "loaded, and it's the not-found case" on first render. Always gate sentinel comparisons on the handle's own existence first. (2) A live-query seed (`untrack(() => handle?.value)`) is only a safe "avoid flashing empty" optimization when the _previous_ value actually describes what's about to be requested — reusing it across a same-instance route-param change (`/collection/A` → `/collection/B`) briefly renders B's screen with A's data. Track which key the cached value belongs to (a plain non-`$state` variable, read/written only inside the seeding effect) and only reuse it when the key matches.

## v0.3.0 task E2 — collections domain (2026-07-29)

- **Factoring the shared "default chart per song" rule paid off immediately**: `repo.ts` now exports `resolveDefaultChartsAndPatterns(doc, songIds)` (batched, no per-song lookup), used by both `listSongsWithDefaultPattern` and `collections.ts`'s `getCollectionWithSongs`. Keeping the rule in one place matters because the library row and a collection row for the same song must always agree on which chart/pattern they summarize — duplicating the `find('Default') ?? earliest-createdAt` logic in two files would have been an easy place for the two to silently drift.
- **`reorderCollection`'s "preserve omitted members" rule needs the omitted items appended in their _existing relative order_, not just any order** — sort the leftover items by their current `position` before appending, otherwise a partial reorder can itself reshuffle songs the caller never mentioned.
- **Export/import's dangling-reference drop only actually fires for a genuinely inconsistent archive** — song id collisions don't produce dangling collection items in practice (a "skipped" song is still present in the target under that id), so the real trigger is a hand-crafted/corrupted manifest missing a song's record entirely. Test it that way (strip the song from `manifest.songs`/`manifest.charts` post-export) rather than via the id-collision path, which doesn't exercise the drop at all.
- **`ImportResult` gained two new required fields (`collectionsImported`/`collectionsSkipped`)** — safe as an additive change for callers that only read fields off the returned object (`settings/+page.svelte` does), but any test asserting via `toEqual` on the whole object needs updating in the same PR, not just `toMatchObject` swapped in — used `toEqual` with the new fields to keep the exhaustive-shape assertion (import assertions across `db.test.ts` and `collections.test.ts` are one thing to grep for if this API changes again).
- **Review fix: any array-of-ids parameter a mutator maps 1:1 onto existing records must dedupe before mapping, not just filter for membership.** `reorderCollection`'s `orderedSongIds.filter((id) => bySongId.has(id))` looked defensive (foreign ids dropped) but a _repeated_ valid id survived the filter and mapped to the same `CollectionItemRecord` object twice — two pushes of one object reference, then `resequence` stomping its `position` field on each pass, silently produced two rows sharing one `id` and one `position` with position 0 missing. The fix is a `Set` of already-taken ids checked during the same pass that builds the ordered list, not a separate `[...new Set(ids)]` pre-pass (order must be preserved). Import is the one place data from an older/buggy version of the app re-enters the store, so the corresponding merge logic (`exportImport.ts`) needs its own independent dedupe (by `(collectionId, songId)`) rather than trusting upstream mutators never produced bad data — otherwise import's resequence step launders exactly this kind of corruption into something that looks valid.
- **Licensing sweep needs to cover titles/author names, not just lyric lines.** The hard "zero copyrighted content" rule (AGENTS.md, `docs/licensing-and-content.md`) extends to test fixtures using real contemporary-worship song titles (e.g. "Goodness of God", "Way Maker", "10,000 Reasons") or artist/author names (e.g. "Bethel Music", "Chris Tomlin") even with no lyrics attached — and to production UI copy (an input placeholder in `MetadataForm.svelte` had one). `grep -rniE "goodness of god|bethel|chris tomlin|way maker|10,000 reasons|hillsong|elevation worship|maverick city"` (extend the alternation per catalog) across `src/**` and `e2e/**` is the fast way to audit; `docs/**` prose _discussing_ the policy with real artist names as examples is fine and out of scope. Public-domain hymns pre-1900 (Amazing Grace/John Newton, Rock of Ages/Augustus Toplady, Isaac Watts as an author name) are safe fixture material; when a fixture only needs _a_ string and isn't meant to look like a real song, a neutral placeholder ("Second Song") is simpler than reaching for another real hymn.

## v0.3.0 task E1 — localStorage store of record (2026-07-29)

- **This repo's vitest config only has a `node` environment project** (`vite.config.ts`'s single `test.projects` entry) — no jsdom/happy-dom, even for `.svelte.ts` files (only files literally named `*.svelte.test.ts` are excluded from the node project, and none exist). `window`/`document`/`indexedDB` are all absent by default. Precedent (`theme.test.ts`) is `vi.stubGlobal`/`vi.unstubAllGlobals` with hand-rolled fakes; for anything needing real `addEventListener`/`dispatchEvent` semantics (this task's cross-tab `storage` event), stub `window` with a genuine `new EventTarget()` — Node has `EventTarget`/`Event` as globals, so `dispatchEvent(Object.assign(new Event('storage'), { key }))` behaves exactly like the browser contract without pulling in a DOM library.
- **`mutate`/`read` both clone via `structuredClone` before exposing the doc** — `mutate` so a throwing mutator or a failed (quota-exceeded) write leaves the cache byte-for-byte untouched (draft is discarded, never swapped in), `read` so a caller mutating a returned record (a real historical Dexie-migration footgun: Dexie always deserializes fresh objects per query, so old code never worried about this) can't silently corrupt the in-memory cache. Given the whole library is a few hundred KB at most, the clone cost is a non-issue.
- **`indexedDB.open(name)` with no version always "succeeds" even when `name` doesn't exist** — it silently creates an empty v1 stub, firing `onupgradeneeded`. The migration reader treats `onupgradeneeded` firing as the signal "there was nothing to migrate" (as opposed to checking `objectStoreNames` alone, which an intentionally-empty real db could also fail) and closes/discards that stub rather than treating it as a real library. `indexedDB.databases()` (supported by fake-indexeddb 6.x and modern browsers) avoids creating the stub in the first place when available; the open-and-check-upgradeneeded path is the required fallback since Safari's support is inconsistent.
- **`fake-indexeddb`'s `indexedDB`/`IDBFactory` are singletons across tests unless reset** — `vi.stubGlobal('indexedDB', new IDBFactory())` in `beforeEach` gives every test a fresh, empty factory. Import `IDBFactory` (the class) from `'fake-indexeddb'`, but reference `indexedDB` (bare, ambient-global — same as the production migration code does) everywhere else in the test, including any local seeding helper; importing the named `indexedDB` binding from `'fake-indexeddb'` instead grabs the _original_ pre-stub singleton and silently desyncs from what the code under test sees after `vi.stubGlobal`.
- **Root `+layout.ts`'s `load()` is the one choke point that's awaited before every route's own load/mount** in this SPA (ssr=false, prerender=true) — the natural place to await a one-shot async boot step (here, IndexedDB→localStorage migration) without teaching every screen about it.

## v0.2.0 task D1 — robust paste (2026-07-28)

- **`share_target.action` in the web manifest must be relative** (e.g. `"share"`, not `"/share"`): it resolves against the _manifest's own URL_, not the origin root or the page that linked it — same mechanism as this manifest's existing `start_url`/`scope`/icon paths (all relative). An absolute `/share` breaks under `BASE_PATH=/lyre` (resolves to the wrong origin-root path); confirmed by inspecting the `BASE_PATH=/lyre` build's `build/manifest.webmanifest` and `build/share.html` output directly rather than trusting memory of the spec.
- **`svelte-check` warns (doesn't error) on reading a `$props()`-destructured value at the top level of a component's `<script>`** ("captures only the initial value… reference it inside a closure instead") — e.g. calling a callback prop once during setup, or passing it straight into a constructor. Doesn't fail `just verify` (warnings don't count as errors there), but wrapping the read in a closure (arrow function, or `$effect`) silences it and is the idiomatic fix.
- **Grab-outcome state (URL field, error copy, guided-paste sheet) factors cleanly into a plain class in a `.svelte.ts` file** (`$state` class fields work fine, same rune rules as a component) — this let the add page's main paste textarea trigger the exact same `grabUrl`/`grabFromHtml` flow `GrabInput.svelte`'s own URL field uses (bare-URL paste, share-target hand-off) without duplicating any of that logic. `db/liveQuery.svelte.ts` was the existing precedent for `.svelte.ts` outside `ui/theme.svelte.ts`'s module-singleton style; this task needed a _per-instance_ version instead, hence the class.
- **`sessionStorage`, not a query param, is the right way to hand data from a redirect-away landing route to its destination in a client-only SPA** (`/share` → `/add`): it survives exactly the one navigation needed and doesn't leak the shared URL/text into `/add`'s own address-bar history. Guard every access behind `typeof sessionStorage === 'undefined'` (same pattern as `ui/theme.svelte.ts`'s `localStorage` guards) so it degrades gracefully in privacy modes that block Storage.
- **Chart-region extraction for noisy pastes is pure line-classification + windowing** — no DOM, no site knowledge: score every line (chord line / section label / pattern-header / lyric-adjacent-to-a-chord-line), slide a window that tolerates small internal gaps (stanza breaks), pick the densest window, optionally pull in a header line just above it. Reused the existing `isChordLine`/`matchSectionLabel` heuristics from `plaintext.ts` rather than re-deriving them — single source of truth for "what looks like a chord line" stays in one place.
